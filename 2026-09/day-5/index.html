⏱ 09:52–09:55 · 3 min
🎤 Matt
  • The machine checks how much of a given implementation plan is implemented in a codebase, and judges it on rigor, fidelity, quality and releasability.
  • Harness: what it can reach. Read the plan and the codebase; the defect tracker; read an API that asks another system for a screenshot of a page on the website; POST to one endpoint to submit its analysis. Nothing else: it can't change the code or the plan.
  • Context: its AGENTS.md gives it the task and the four criteria, and tells it how to find the plan it has to evaluate. Everything else it reads when it needs it. It has no way to see the doer's conversation, so it judges the work, not the story.
  • In Böckeler's words: AGENTS.md is a guide, steering it before it acts. The screenshots and the defect tracker are how it observes the software. The machine itself is a sensor for the line (feedback after the doer acts), and an inferential one: a model's judgement, not a script.
  • Point at the one coral box: the only thing it can write. Narrow permissions are part of the harness.
  • Open: can it write to the defect tracker (file issues), or only read it?

The three big brains: one review, three providers' models, at the same time

⏱ 10:35–10:47 · 12 min
🎤 David
  • Show the iteration 005 line in an instructor-built factory: the doer fans out to three reviewers, which run at the same time, and they fan in to the synthesiser, which decides. The line routes on the synthesiser's result as it did on the validator's.
  • Use prepared runs: one in progress, showing the reviewers working at once, and one finished, showing the synthesiser's result. Recorded fallback if the live run fails.
  • Point out that fanning out is the factory's new ability. The three big brains is one choice of what to fan out to; the reviewers being alike is that line's choice.
  • Ask: “Where would your project want more than one opinion?”
  • The tutorial gives specifications, not an implementation: this has to be an instructor-built factory.
