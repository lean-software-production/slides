🎤 Aldric
  • The diagram from the top of therecsfiles.dev (which uses a library example), redrawn for the plot register.
  • Real records in the plot register: the vision, UL-2: Gardener, UL-3: Waiting list, UW-2: Give up a plot and F-2: A gardener can give up a plot. Extrapolated for the example, not in the fixture: F-3, MSG-1 and MSG-2. Say so if someone asks.
  • Read it from the middle: the user workflow is what a person is trying to do, so it's where you orient. It names the features it reaches, the messages it can end in, and the words it uses. The vision sits above everything.
  • What each kind holds: ubiquitous language, what a word means and nothing about behaviour (Evans); user workflow, what a person is trying to do, step by step (Cockburn); feature, what the system does, one rule to a sentence (Mavin's EARS); message, the exact text of a refusal or failure.
  • Not drawn: architectural decisions (ADR), a pattern the code follows and why (Nygard). An ADR names words and other ADRs, like ADR-3: A plot is identified by its bed number.
  • Every record is short, numbered, one thing each, in a file of its own, and always cited by number and title. A record's title is a headline.
  • Transition from the problems: “So what stops the agent inventing? It has somewhere to look. The recs files are skills that have the agent keep each decision as a record, and work from those records.”
  • “Everything that follows uses one project, the plot register: a community garden that allocates plots and keeps a waiting list.”
  • Placement test, if asked: if a word would survive a rewrite of the code, it's ubiquitous language; if the rewrite would retire it (“SQLite”), it belongs in a decision.
  • One more rule, for code: a comment is a citation of a record and nothing else, like # F-1 §2: A gardener can be allocated a free plot.

⏱ 12:13–12:15 · 2 min
🎤 Aldric
  • The ubiquitous language: each term is a record of its own, a sentence or two on what the word means and nothing about behaviour.
  • The agent speaks in those words, to you and in the code it names. Where it needs a word the records don't have, it builds one from existing words first, proposes candidates, and waits; nothing new is written before you agree to the word.
  • For an existing codebase, recs-kickstart collects the words the code uses today and lists the renames the records call for.

⏱ 12:15–12:16 · 1 min
🎤 Aldric
  • A rename changes a word's spelling: every occurrence is replaced. A redefinition keeps the spelling and changes the meaning, so nothing announces which sentences went wrong; each hit has to be judged.
  • The agent writes the rule that tells a false sentence from a true one first, before reading any hit. Then it searches the stem, not a phrase, counts the hits, and gives every one a verdict: its replacement, or “stands” with the reason.
  • Then the team agrees, rewords, or declines. Nothing changes before that.
  • The 50 hits are counted in the live fixture; the records extrapolated on the diagram aren't in it.

⏱ 12:18–12:19 · 1 min
🎤 Aldric
  • The same two functions, once the team has answered the question: say they decided returning gardeners skip the list. That decision is now a record, and both places cite it, so the next session reads one rule, not two. The team could just as well have decided the opposite; the point is that someone decided.
  • F-4 is extrapolated for the example, like the records on the diagram. The team would also agree on the words “returning gardener” first.
  • Two kinds of comment are allowed: a citation of a record by number and title, or a pointer to a heading of the project's knowledge base where the code does something whose reason it doesn't show. No third kind.
  • No explanation, no warning, no paraphrase of the record. A paraphrase goes stale; the citation can't. When the record is superseded, the sweep repoints the citation. Tests follow the same rule.
  • Elixir here for brevity.

⏱ 12:19–12:22 · 3 min
🎤 Aldric
  • From the “Records are read from disk” section of the AGENTS.md that recs-kickstart writes: open a record's file before citing it, measuring code against it, or framing a question with it. Open each record that bears, and no others.
  • A record bears if the task names it, a record you opened names it, or the code you're changing cites it. A title that only sounds near the work is opened to find out.
  • Whatever AGENTS.md itself copies in, the session and every subagent carry for the whole session, and that copy is stale the moment a record changes. So the agent cites what the file on disk says.
  • Small files keep this cheap: one record per file, and one term per file. Opening a word costs one short file, not the whole glossary.
  • recs-subagent-driven-development: the controller hands each subagent its task with the records the task cites, so the subagent starts with what it needs and nothing else.

⏱ 12:23–12:24 · 1 min
🎤 Aldric
  • “Same situation as the last slide. This time the agent starts from the records.” Both records are real, word for word from the plot register.
  • How the agent got here: it read the projections, opened the records the workflow step names (F-2: A gardener can give up a plot), then the words those records use (UL-1: Plot), and checked each sentence against the step it was planning.
  • The rule it follows: where the plan and a record disagree, the record wins. The plan stops at the disagreement, and the agent never plans around a record or edits one to fit.
  • Every skill in the development flow does the same check at its own stage: brainstorming, writing a plan, executing it, code review, debugging. A plan can also meet code that disagrees with a record; that goes to the record keeper first too.
