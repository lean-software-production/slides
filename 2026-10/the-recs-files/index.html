  • What each kind holds: ubiquitous language, what a word means and nothing about behaviour (Evans); user workflow, what a person is trying to do, step by step (Cockburn); feature, what the system does, one rule to a sentence (Mavin's EARS); message, the exact text of a refusal or failure.

  • Placement test, if asked: if a word would survive a rewrite of the code, it's ubiquitous language; if the rewrite would retire it (“SQLite”), it belongs in a decision.
  • One more rule, for code: a comment is a citation of a record and nothing else, like # F-1 §2: A gardener can be allocated a free plot.

🎤 Aldric
  • From the “Records are read from disk” section of the AGENTS.md that recs-kickstart writes: open a record's file before citing it, measuring code against it, or framing a question with it. Open each record that bears, and no others.
  • A record bears if the task names it, a record you opened names it, or the code you're changing cites it. A title that only sounds near the work is opened to find out.
  • Whatever AGENTS.md itself copies in, the session and every subagent carry for the whole session, and that copy is stale the moment a record changes. So the agent cites what the file on disk says.
  • Small files keep this cheap: one record per file, and one term per file. Opening a word costs one short file, not the whole glossary.
  • recs-subagent-driven-development: the controller hands each subagent its task with the records the task cites, so the subagent starts with what it needs and nothing else.

  • “I forked obra's superpowers workflow and adapted it so it's record-first. It has been working fantastically.”
  • superpowers is Jesse Vincent's (github.com/obra/superpowers), MIT, like the recs files.
  • The recs versions: brainstorming, writing plans, executing plans, subagent-driven development, test-driven development, systematic debugging, requesting and receiving code review, verification before completion, finishing a branch, git worktrees. Where a recs skill and a superpowers skill do the same job, the project's AGENTS.md says to use the recs one.
  • What changes in practice: a plan names the records each task realizes; the only comment allowed in code is a citation of a record; review and debugging treat code that disagrees with a record as a question for the record keeper first.
  • If asked: the README says these development-flow skills may still change before 1.0, perhaps split into a generic flow and a part for each realization modality. The record forms and record management are the stable part.

A comment is a citation

lib/plot_register.ex
# F-2 §1: A gardener can give up a plot
def give_up(plot, [next | rest]), do: {%{plot | holder: next}, rest}

# F-2 §2: A gardener can give up a plot
def give_up(plot, []), do: {%{plot | holder: nil}, []}

Number, section and title, and nothing else. The rule lives in the record.

⏱ 12:28–12:29 · 1 min
🎤 Aldric
  • The two clauses realize the two requirements of F-2: A gardener can give up a plot: §1, the first gardener on the waiting list becomes the holder and leaves the list; §2, with nobody waiting, the plot is free.
  • The rule in the project's AGENTS.md: a comment points at a record, by number and title, or at a heading of the knowledge base where the code does something whose reason it doesn't show. No third kind.
  • No explanation, no warning, no paraphrase of the record. A paraphrase goes stale; the citation can't. When the record is superseded, the sweep repoints the citation to its successor.
  • The same applies to tests: the record a check rests on is a citation above it.
  • Elixir here for brevity; the plot register's own code in the repo is Python, with the same comments.
